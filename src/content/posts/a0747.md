ailx10说：这篇是我2024年5月写的。调研 SOAR 时，我看见 Blink 列了三千多条安全预案，第一反应就是想知道，这个数量究竟怎么来的。于是按分类往里翻，看看一条模板里有几步、通知方式怎样拆、同一动作是否在不同分类里反复出现。走了一遍，才发现数字背后有不少很细的 API 动作和组合方式。这篇写的不是否定某个产品，而是一次带着疑问拆目录的过程：当“数量很多”成为卖点，把其中几条真正展开，比只盯着首页的大数字更能理解它在提供什么。

---

原文统计了截至 2023 年末的 Blink SOAR Security 模板，并分析大量预案数量可能产生的原因；统计是历史快照。

1. 合规1173(21)
2. 威胁狩猎461(25)
3. 终端安全458(24)
4. 云安全329(31)
5. SOC事件响应300(23)
6. 身份访问278(24)
7. 网络安全243(15)
8. 数据安全199(21)
9. 漏洞管理174(11)
10. SaaS安全166(19)
11. ......

![](/notes-assets/c70d15c4f3e8b14da08a.webp)

作者提出三种可能因素，以下属于观察和推测，并非严格去重结论。

1. 从整体来看，1个设备2\~10个预案动作是常态，比如终端安全的Apex One有5个，威胁狩猎的VirusTotal有7个，网络安全的FortiGate有10个。但是，1个设备能有超过100\+个预案，那肯定是直接把设备的API业务接口集成进来，典型的就是合规，这是造成SOAR预案数量整体偏高的根本原因。
2. 从细节来看，2个预案可能是同1个动作，仅仅是发送通知的方式不同，造成预案数量翻倍。如果砍一半，再除去合规1000个，核心预案也就800个，150种设备，平均1个设备5～6个预案，也不是很多。此外，1个预案可能分布在多个子分类中，造成单独看子分类的预案数量，有一种感觉很多的视觉效果，实际上都是重复而已。
3. 从开发者角度来看，90%以上的Blink SOAR预案都是2个步骤的简单playbook，保证顺利完成**KPI**，嘻嘻：

![](/notes-assets/4a72a1c4e359345ad011.webp)

- **COMPLIANCE \& GOVERNANCE：**合规有1173个预案，涉及21个设备，96%都是2个步骤的简单playbook。
- **ENDPOINT SECURITY：**终端安全有458个预案，涉及24个设备，99%都是2个步骤的简单playbook，一个动作拆分成2个预案，实际平均1个设备不到10个预案动作。最少的，比如赛门铁克EDR，只有1个预案动作。最多的，比如下一代Apple设备管理平台 Kandji ，有27个预案动作。居中的，比如趋势科技的EDR产品Apex One，有5个预案动作。
- **THREAT HUNTING：**威胁情报有461个预案，涉及26个设备，Shodan有18个预案动作，VirusTotal有7个预案动作，Rapid7有7个预案动作。
- **NETWORK SECURITY：**网络安全有243个预案，涉及15个设备，和上面类似，基本都是2个步骤的简单playbook，最少的，比如静态源代码分析服务平台Veracode只有1个预案动作。最多的，比如云安全平台Check Point Cloud Guard有26个预案动作。居中的，比如Palo Alto Firewall防火墙有16个预案动作，FortiGate飞塔防火墙有10个预案动作。

![](/notes-assets/01f30194f7a73490f5a8.webp)

拆分与重复会影响计数，却不能靠随手砍半给出真实覆盖率。真正有用的比较，是哪些输入能触发哪些动作，以及异常时流程还能不能把事情做完。
