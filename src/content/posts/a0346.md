ailx10说：这篇是2022年1月之前写的，后来又改过。试 LOIC 时，我把 HTTP 和 TCP 两种模式都对着自己的蜜罐环境跑，边看请求和包数，边观察延迟。流量确实出来了，但目标的反应没想象中剧烈，这种“不够热闹”的结果也值得写下来。抓包又让我注意到 ACK 和真实源地址，和工具介绍里的印象未必一样。这篇主要留的是一次亲自比对：工具说自己能做什么、线上实际发了什么、目标又有什么变化，三件事放在一起，才比单独贴一个很大的数字更能说明实验。

---

本文记录在虚拟机中对自建蜜罐进行的 LOIC 流量测试。工具提供 HTTP、TCP 和 UDP 模式；单次结果只反映当时的环境，不代表其他系统的容量或工具的普遍效果。

这个软件是大小才133k，需要.net 4.0的支持，打开界面也是非常简单的，有一个URL地址和IP地址，这里我都填写的是我的蜜罐地址，然后Method方法可以选择HTTP、TCP和UDP。可以自定义线程数，默认是10个线程。还可以选择速度，快速或慢速，可以自由拖动。TCP和UDP的载荷可以自由定义，默认是`A cat is fine too. Desudesudesu~` ，然后点击右上角的按钮，就启动了。

![](/notes-assets/ade4b86d80b0be928958.jpg)

还没有进行测试的时候，测了一下网络时延。

![](/notes-assets/90221925c3c9ec074e2e.webp)

原实验发出约 1000 次 HTTP 请求后再次测量网络时延，未观察到明显变化；该指标不能单独衡量 Web 服务的可用性。

![](/notes-assets/e0766d726be5622814b0.webp)

通过wireshark抓包，发现HTTP包的速率上来的很慢。

![](/notes-assets/a3dfa587541d3fa3ae76.jpg)

原实验随后切换 TCP 模式，记录约 60 万个数据包，并观察网络时延。时延的变化不足以单独证明应用服务是否受到影响。

![](/notes-assets/ae39bc26d778d6aeb8b1.webp)

抓包记录中观察到大量 ACK 报文及真实源 IP；仅凭 ACK 标志不能认定完整的 ACK flood 机制，也不能据此判断所有流量的来源。

![](/notes-assets/7c073426960a994874f1.jpg)

若要评估服务可用性，还应结合吞吐量、响应时间、错误率和服务端资源，在授权实验环境中设置对照。

这次影响不大，就保留这个结果，而不是为了符合“攻击”二字硬写成瘫痪。实际源地址、报文形态和延迟一起看，才能知道工具在这套条件下真正做了什么。
