ailx10说：这篇是2025年5月之前写的，后来又改过。第一份主机打分交底书之后一周，我又写了事件可信度，几年后回想，第二份反而更难还原。起点是很实际的烦恼：规则是静态的，客户场景却会变，同一个“异常”关键字，在金融页面和医疗报告里可能完全不是一回事。我试着把一段时间的流量变化和告警出现关系放在一起，给告警多一个观察角度。文章记录这份旧想法，也保留记忆的局限；回头看，最想解决的始终不是再加一条规则，而是让系统少一点不问场景就急着下判断。

---

可信度回顾以七天小时流量六特征3sigma标异常，与告警发生序列计算相关和条件发生概率，低于50%判误报。

## 前提和待核查点

P告警发生给定流量不是P真实攻击给定告警，缺真值校准；3sigma分布相关门槛多重比较与零分母需说明。

## 历史笔记与实验记录

继2020年10月15日，我提交的第一篇专利交底书（ailx10：安全态势感知中的主机关注度打分思考），一周之后，也就是2020年10月22日，我又提交了一篇专利交底书，现在也已经审定授权了。说实话，第一篇没啥经验，写的很水，竟然通过了，但是第二篇专利就比较难了，回忆起来也比较困难，可能无法完全还原当初的想法。

我观察到当时产品的一个痛点，包括现在依然是众多态势感知产品的一个痛点，那就是静态的规则，无法适应动态的场景，规则是死的，但是环境是活的，同样的告警在A环境下可能是误报，在B环境下可能是恶意的，举一个最简单的例子你就明白了，比如一个Web告警，HTTP响应内容中检测到“异常”关键字，在金融场景可以判定为攻击失败，但是在医疗场景就不一定了，因为很多人的报告单上可能有各种疾病“异常”。所以，规则和场景之间是存在一定的关联关系的，而我在2020年就开始试图通过一个算法，来解决这种动态场景下的静态规则的误报问题。

在了解这个告警可信度算法之前，先了解一下几个知识点：

（1）皮尔逊相关系数，如果一组数据与另一组数据的皮值绝对值在0.5到1之间，那么这两组数据是强相关的。

| 相关性 | 负 | 正 |
| --- | --- | --- |
| 无 | -0.09 ～ 0 | 0 ～ 0.09 |
| 弱 | -0.3 ～ -0.1 | 0.1 ～ 0.3 |
| 中 | -0.5 ～ -0.3 | 0.3 ～ 0.5 |
| 强 | -1 ～ -0.5 | 0.5 ～ 1 |

![](/notes-assets/32b3fe11f3f1e1d2d54a.webp)

（2）再了解一下3sigma异常检测，用于寻找一组数据中的异常点，超过3sigma上界或下界都认为是异常点。

![](/notes-assets/9491411cc6ee919faecf.webp)

（3）最后了解一下概率论，假设A事件的概率是0.3，B事件的概率是0.4，AB同时发生的概率是0.2，那么A事件发生的前提下，B事件发生的概率等于0.667，下图是做100万次模拟实验的预测结果，P(B\|A)也收敛在0.667。

```
P(B|A) = P(AB)/P(A) = 0.2/0.3 = 0.667
```

![](/notes-assets/e4e471bcf6460cbef91a.webp)

接下来，开始介绍5年前我设计的告警可信度算法：

（1）最近7天的时间窗口，以小时为单位，统计流量行为特征，假设有以下6个特征

| 时间片 | 源IP地址数 | 目的IP地址数 | 上行字节数 | 下行字节数 | 目的国家数 | 目的城市数 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 |  |  |  |  |  |  |
| 2 |  |  |  |  |  |  |
| 3 |  |  |  |  |  |  |
| 4 |  |  |  |  |  |  |
| 5 |  |  |  |  |  |  |
| 6 |  |  |  |  |  |  |
| ... |  |  |  |  |  |  |
| 168 |  |  |  |  |  |  |

针对每一个特征的168个分片，用3sigma异常检测算法，得到异常值的上下限，并评估第169个时间片。

如果第169个时间片中的特征值不是异常，则标记为正常，否则标记为异常。

如果6个特征值中至少存在1个异常，则该时间片综合标记为异常，否则标记为正常。

| 时间片 | 源IP地址数 | 目的IP地址数 | 上行字节数 | 下行字节数 | 目的国家数 | 目的城市数 | 综合流量标记 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 169 |  |  |  |  |  |  |  |
| 170 |  |  |  |  |  |  |  |
| 171 |  |  |  |  |  |  |  |
| ... |  |  |  |  |  |  |  |

（2）针对所有的安全事件进行相关系数计算，筛选目标安全事件

假设有以下安全事件，记录每一个时间片安全事件的发生状态

| 时间片 | 安全事件名称 | 安全事件发生状态 |
| --- | --- | --- |
| 169 | XSS攻击 |  |
| 169 | SQL注入 |  |
| 169 | 文件上传 |  |
| 169 | 代码执行 |  |
| 169 | 命令执行 |  |
| 169 | 信息泄露 |  |
| ... |  |  |

那么，针对每一个安全事件，我们就能得到两组数据：综合流量标记和安全事件发生状态。顺理成章的，我们就可以使用皮尔逊相关系数，得出部分安全事件发生状态和综合流量标记是强相关的。也就是说该安全事件的发生，极大可能伴随着综合流量标记的异常。比如：假设信息泄露事件发生状态和综合流量标记皮尔逊相关系数大于0.5，那么当发生信息泄露事件，就会伴随流量特征异常。

| 时间片 | 综合流量标记 | 安全事件发生状态 | 皮尔逊相关系数 |
| --- | --- | --- | --- |
| 1 |  |  |  |
| 2 |  |  |  |
| 3 |  |  |  |
| ... |  |  |  |
| 168 |  |  |  |
| 169 |  |  |  |
| 170 |  |  |  |

（3）计算在综合流量正常或异常的前提下，目标安全事件出现的概率

统计最近168个时间片的综合流量标记，计算异常时间片出现的概率，定义为P(A1)

统计最近168个时间片的综合流量标记，计算正常时间片出现的概率，定义为P(A2)

统计最近168个时间片的目标安全事件的发生状态，计算安全事件出现的概率，定义为P(B)

统计最近168个时间片的综合流量标记异常，且出现目标安全事件，定义为P(A1B)

统计最近168个时间片的综合流量标记正常，且出现目标安全事件，定义为P(A2B)

那么当第169个时间片的综合流量标记异常时，目标安全事件发生的概率为P(B\|A1) \= P(A1B)/P(A1)

那么当第169个时间片的综合流量标记正常时，目标安全事件发生的概率为P(B\|A2) \=P(A2B)/P(A2)

注意：这里P(A1)和P(A2)要求大于0，等于0的暂且忽略

观察169时间片，我们可以得到类似下面的表格：

| 时间片 | 目标安全事件 | 综合流量标记 | 安全事件状态 | 条件概率 |
| --- | --- | --- | --- | --- |
| 169 | SQL注入 | 异常 | 发生 | 80% |
| 169 | SQL注入 | 正常 | 发生 | 10% |

原方案将某条件概率低于 50% 作为疑似误报规则，但 P(告警发生｜流量特征) 并非 P(攻击真实｜告警)。该阈值需要用人工标注的真值、误报率及漏报率校准，不能直接定义真实或误报。

所以，169时间片综合流量异常的情况下，SQL注入事件发生的条件概率是80%

169时间片综合流量正常的情况下，SQL注入事件发生的条件概率是10%

综上，只需要观察综合流量是否正常，就能计算出目标安全事件发生的条件概率，这就是我5年前设计的动态背景流量条件下的安全事件可信度计算方法，设计思想放到今天也是遥遥领先的存在。但是，实网环境中是不可能给态势感知产品上传完整的流量信息，因为数据量太大了，价值不高，但存储成本很高，所以，具体落地有难度。

低于某个比例不自动等于误报，先验与真值仍要核对。让分数回到它真正衡量的事件上，才能避免一个数学表达把判断包装得过于确定。
