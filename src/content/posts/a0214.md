ailx10说：这篇是我2023年9月写的。这次研究旧 Nginx 的文件名处理，我是从上传一个看起来不是 PHP 的文件开始的。上传时检查一种名字，访问时又按另一种路径去解释，两边的判断错了位，才有了后面执行脚本的机会。我把请求里的特殊字符、访问方式和连接结果连着记下来，也遇到了响应不直观的情况。做完后更想弄清的不是某个后缀有多神奇，而是上传过滤和服务器解析到底各自看见了什么；页面报错或超时，也不能单独当成成功与否的答案。

---

下面是Vulhub的官方解释：

这个漏洞其实和代码执行没有太大关系，其主要原因是错误地解析了请求的URI，错误地获取到用户请求的文件名，导致出现权限绕过、代码执行。举个例子，比如，Nginx匹配到.php结尾的请求，就发送给fastcgi进行解析，常见的写法如下：[\[1\]](#ref_1)

```
location ~ \.php$ {

    include        fastcgi_params;



    fastcgi_pass   127.0.0.1:9000;

    fastcgi_index  index.php;

    fastcgi_param  SCRIPT_FILENAME  /var/www/html$fastcgi_script_name;

    fastcgi_param  DOCUMENT_ROOT /var/www/html;

}
```

正常情况下，只有.php后缀的文件才会被发送给fastcgi解析。而存在CVE-2013-4547的情况下，我们请求`1.gif[0x20][0x00].php`，这个URI可以匹配上正则`\.php$`，可以进入这个Location块；但进入后，Nginx却错误地认为请求的文件是`1.gif[0x20]`，就设置其为`SCRIPT_FILENAME`的值发送给fastcgi。fastcgi根据`SCRIPT_FILENAME`的值进行解析，最后造成了解析漏洞。所以，我们只需要上传一个空格结尾的文件，即可使PHP解析之。

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

- `docker-compose down`
