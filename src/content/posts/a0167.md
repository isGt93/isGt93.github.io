ailx10说：这篇是我2024年12月写的。wife\_wife 这题让我认真看了一次 Object.assign 到底把东西合到了哪里。注册输入先检查自身属性，后面又拿去合并成新用户，我就沿着 JSON 和原型链继续试，最后让新对象从原型上读到 isAdmin。这篇把核心注册代码和对象变化放在一起，比只说一句“原型链污染”更好回看。真正卡人的地方是，检查时看到的输入和使用时读到的属性不一定来自同一处；弄清谁是对象自己的值、谁是继承来的，题目的门才算真正打开。

编辑核查提示：只依据现有片段，不能断言全局 Object.prototype 被修改；baseUser 是否已有 isAdmin 自有属性等条件会改变结论。 本稿保留历史题目截图及代码，未在原题环境重新运行；截图内容和水印、引用链接仍需发布前复核。

本文讨论 JavaScript 对象合并与原型链的风险。普通对象会沿原型链查找属性，但不是所有对象最终都以 Object.prototype 为原型；例如 null 原型对象没有普通原型链。

不当使用`Object.setPrototypeOf`, `__proto__`或者`Object.create` 这些API可以用来改变对象的原型。如果应用逻辑错误地允许外部输入来设置对象的原型，则可能发生原型链污染。

尝试 JavaScript 原型链污染，这里的`__proto__`是一个特殊的属性，指向对象的原型，具体为啥这样修改，要看源码才行，这个地方创建的其实就是一个叫`admin`的普通用户。

```
{
    "username":"admin","password":"admin",
    "__proto__":{
        "isAdmin":true
    }
}
```

![](/notes-assets/2050d6ff17b459fb9432.webp)

原文从外部找到的注册代码显示，用户输入参与了对象合并；结合具体对象结构，可以分析管理员检查与属性继承之间的差异。

当 JSON 解析结果包含自身的 \_\_proto\_\_ 属性时，Object.assign 对普通目标对象赋值可能触发继承的 setter，从而改变该目标对象的原型。实际的 isAdmin 读取结果还取决于目标对象是否有同名自有属性；这不等于必然修改全局 Object.prototype。

```
app.post('/register', (req, res) => {
    let user = JSON.parse(req.body)
    if (!user.username || !user.password) {
        return res.json({ msg: 'empty username or password', err: true })
    }
    if (users.filter(u => u.username == user.username).length) {
        return res.json({ msg: 'username already exists', err: true })
    }
    if (user.isAdmin && user.inviteCode != INVITE_CODE) {
        user.isAdmin = false
        return res.json({ msg: 'invalid invite code', err: true })
    }
    let newUser = Object.assign({}, baseUser, user) //就是这里，JavaScript 原型链污染
    users.push(newUser)
    res.json({ msg: 'user created successfully', err: false })
})
```

原型链问题不只是一个特殊键名，而是检查口径和使用口径不一致。把合并前后的对象状态摊开，权限判断为什么变了就能被具体解释。
