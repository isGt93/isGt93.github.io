ailx10说：这篇是2019年12月之前写的，后来又改过。这篇逻辑漏洞，是我在一个自建页面里做的对照。POST 登录分支检查账号口令，看起来像是有门槛；可 GET 查询个人资料的分支没有检查会话和访问权限，换个名字就把本不该看到的信息送了出来。我把两段逻辑放在一起，是想说明问题有时不在单个密码框，而在另一个入口绕开了整套流程。做完再看，数据库一直连着不是核心原因，真正缺的是对“你是谁、能查谁”的判断，页面回什么字段也得认真想。

---

一个系统即使提供登录页面，也可能在其他请求分支遗漏权限检查。历史实验中，登录使用 POST 校验口令，但读取个人资料的 GET 分支直接根据用户名查询并返回数据。

## 问题发生在哪里

正常流程是用户登录后查看自己的资料。实验发现，若访问资料的请求只依赖 URL 中的 `name` 参数，而服务端既不检查当前会话，也不验证该会话是否有权读取目标用户，就可能返回其他人的资料。

```text
登录分支：校验提交的用户名和口令
资料分支：接收 name → 查询并输出资料
缺口：资料分支没有把请求与已认证用户及其权限绑定
```

这不是因为数据库连接“保持打开”而产生越权。数据库连接负责访问数据，认证和对象级授权需要应用在每次相关请求中执行。实验代码还把输入拼入 SQL，并返回明文密码字段；这是另外两类需要处理的问题。

## 如何修复

对每次资料请求验证有效会话，并在服务端检查当前用户是否有权访问目标记录；不要依赖隐藏按钮或前端传入的用户名作为授权依据。数据库查询使用参数化接口，只返回业务所需字段；密码应使用适当的密码哈希方案保存，不能在资料响应中返回。

## 原实验代码补充

以下代码用于说明历史实验的请求路径和处理逻辑，保留原有漏洞与旧版本写法。数据库密码已在原存档中隐藏；涉及外网地址的示例已替换为示例域名，具体环境需自行配置。


```php
// login.php by ailx10
<?php
$con=mysqli_connect("localhost","root","***","hack2018");
if( !$con )
{
   exit("error:" . mysqli_connect_error());
}

if(isset($_GET["name"]))
{
    $name = $_GET["name"];

    $result = mysqli_query($con,"select * from login where `name` = '" . $name . "'");
    $row = mysqli_fetch_array($result);
    if($row)
    {
        echo "success!<br />";
        echo "name:" . $row["name"] . "<br />";
        echo "passwd:" . $row["passwd"] . "<br />";
        echo "school:" . $row["school"] . "<br />";
    }
    else
    {
        exit("faild");
    }

}
else
{
    $name = $_POST["name"];
    $passwd = $_POST["passwd"];

    $result = mysqli_query($con,"select * from login where `name` = '"
              . $name . "' and `passwd` = '" . $passwd .  "'");
    $row = mysqli_fetch_array($result);
    if($row)
    {
        echo "success!<br />";
        echo "<a href='login.php?name=" . $name . "'>Your info</a>";
    }
    else
    {
        exit("faild");
    }
}

?>
```

同一个站点里，一处认证成立不代表另一处授权自动跟上。把每个对象接口自己的身份检查列出来，逻辑漏洞就能从模糊直觉变成具体缺少的判断。
