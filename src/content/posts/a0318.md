ailx10说：这篇是2019年12月之前写的，后来又改过。这篇我把文件上传的判断条件改成 Content-Type，想看看服务端相信这个值会发生什么。抓包以后，只改文件部件声明的类型，内容并没有因此变成真正的图片，却照样可能通过检查。这样一对照，客户端写在请求里的标签和实际文件就很容易分开了。笔记也留下 multipart 里不同层次的头，免得把整个请求和单个文件的声明混起来。它不是一个新奇技巧，更多是在提醒我，用户替自己贴的“我是图片”不能直接拿来当证据。

---

上传只信$\_FILES.type的GIF/JPEG白名单，可改multipart部件Content-Type让任意内容通过并原名存储。

阅读说明：应区分顶层multipart请求头和单文件part的Content-Type；客户端声明不能证明文件内容，后续执行仍取决文件名映射。 原实验环境和代码未重新运行，涉及截图的关键细节仍待核对。

本例讨论服务端信任 multipart 上传文件部分的 Content-Type 声明。该字段由客户端提供，不能单独证明文件内容的真实类型。

---

代理工具可以修改上传文件部分的 Content-Type；服务端是否接受以及后续是否执行，仍取决于实际校验和解析配置。

![](/notes-assets/67f26b02715f3ec1a199.jpg)

将`application/octet-stream`修改成`image/jpeg`，成功绕过。

---

前端代码：

```
<!-- index3.html by ailx10 -->
<html>
<head>
<title>ailx10</title>
</head>
<body>



<form action="upload3.php" method="post" enctype="multipart/form-data">
<label for="file">FileName:</label>
<input type="file" name="file" id="file"  value="file"  /><br />
<input type="submit" name="submit" value="submit" />
</form>
</body>
</html>
```

后台代码：

```
// upload3.php by ailx10
<?php
if($_FILES["file"]["error"] > 0)
{
    echo "Return Code:" . $_FILES["file"]["error"] . "<br />";
}
else
{
    if(($_FILES["file"]["type"] != "image/gif")
    &&($_FILES["file"]["type"] != "image/jpeg")
    &&($_FILES["file"]["type"] != "image/pjpeg"))
    {
        exit($_FILES["file"]["type"] ." " .  "Not allowed suffixes");
    }

    echo "Upload:" . $_FILES["file"]["name"] . "<br />";
    echo "Type:" . $_FILES["file"]["type"] . "<br />";
    echo "Size:" . ($_FILES["file"]["size"]/1024) . " kb<br />";
    echo "Temp file:" . $_FILES["file"]["tmp_name"] . "<br />";
    if(file_exists("upload/" . $_FILES["file"]["name"]))
    {
        echo $_FILES["file"]["name"] . "already exists.";
    }
    else
    {
        move_uploaded_file($_FILES["file"]["tmp_name"],"upload/" . $_FILES["file"]["name"]);
        echo "Stored in:" . "upload/" . $_FILES["file"]["name"];
    }
}
?>
```

请求里写着image并不代表内容已经被可信地识别。把客户端声明、实际文件与保存路径分开检查，上传逻辑才不会只是在替用户重复一遍自我介绍。
