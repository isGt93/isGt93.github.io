ailx10说：这篇是2019年12月之前写的，后来又改过。命令执行这一篇，我故意做了一个简单的 Ping 页面，把输入的 IP 直接接到命令后面。正常地址时看不出异样，换上能改变 shell 语义的内容，输入就不再只是参数，后面跟着执行了别的动作。两行后端代码摆出来，问题反而比一长串漏洞名更直白。我想借这个小练习记住那条界线：程序以为自己在接收数据，实际上把解释规则也一并交出去了。看懂输入在哪里变成语法，比光记住几个分隔符更容易迁移到别的场景。

---

命令注入发生在应用把外部输入交给命令解释器时：原本应当作为数据处理的内容，被解释成了命令语法。历史实验使用一个接收地址并执行 Ping 的 PHP 页面说明这一问题。

## 实验中的问题

后端的核心写法如下，输入直接拼入命令字符串：

```php
echo system("ping -c 1 " . $_POST["ip"]);
```

当输入包含管道等 shell 特殊字符时，解释器可能将其当作命令结构，而不是 Ping 的目标参数。具体影响取决于操作系统、shell、PHP 配置和进程权限。原实验使用隔离靶场来观察额外命令的输出；不应在未获授权的系统上测试。

`system()` 是 PHP 提供的函数，不应在此处笼统称为内核系统调用。原文用 `/etc/passwd` 作为文件示例，但它不是现代 Linux 通常保存密码散列的位置；能否读取及读取后的影响也取决于实际权限。

## 如何避免

优先使用不需要调用 shell 的实现。如果必须启动外部程序，应使用能够分别传入程序和参数的接口，避免将输入拼成命令行；同时对地址或域名按业务需求做严格校验、限制进程权限，并控制执行时间与输出。具体 API 的 shell 行为应查阅所用语言和系统的文档。
