ailx10说：这篇是我2024年4月写的。又见到 Nessus 的扫描载荷时，我想起自己 2020 年还装过它、做过联动实验。这次响应明明是 503，内容里却带着一段脚本，让我忍不住多看了一眼。于是把返回内容保存下来，换成 HTML 形式打开，果然看到了弹窗，也把插件名那条线索记住了。这篇写的是这点“状态码看着失败，内容又很有意思”的别扭感。它促使我继续区分原始响应和后续打开方式，不能只盯着一处显眼的结果就省掉中间发生的事。

说起 nessus 漏洞扫描工具，那已经是2020年的事情了

- ailx10：Nessus漏扫软件安装
- ailx10：Mulval与Nessus联动

上周遇到一个 nessus 的漏洞扫描载荷，响应是一个 503 Service Unavailable ，但是响应内容中包含的 xss 语句，貌似可以触发，简单纪录一下。这里非常重要有一点，nessus 是如何判断 xss 攻击成功的？有没有做漏扫的小伙伴知道。

请求载荷：

```
GET /pay/goods/nessus"><script>alert('django_admin_xss.nasl')</script>/ HTTP/1.0
```

响应内容：

```
{"timestamp":"2024-04-11 18:56:01","path":"/pay/goods/nessus"><script>alert('django_admin_xss.nasl')</script>/","status":503,"error":"Service Unavailable","message":"Unable to find instance for xzhi-pay"}
```

将 JSON 响应另存为 HTML 后出现脚本弹窗；这一操作改变了浏览器解释上下文，不能单独证明原接口存在可利用 XSS。

![](/notes-assets/07d90d71ba5e73127b9f.webp)

复现时自己改变了内容类型，就不能把结果原封不动算到原接口头上。保留响应头和实际消费路径，才有办法判断这里是可利用XSS还是一次展示误差。
