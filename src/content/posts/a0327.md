ailx10说：这篇是2019年12月之前写的，后来又改过。SSRF 我没有只列危害，而是搭了一个让服务端 curl 指定 URL 的小页面。先取远端网页，再换 file 路径，看到返回的内容发生变化，才更清楚真正去访问资源的是服务器，不是眼前的浏览器。文章也记了某些页面没加载成功的情况，但当时没有完全找到原因。对我来说，这个练习最大的帮助是换了观察位置：我能直接访问什么，与服务器所在的网络和它能读的文件，不一定是一套范围。

---

服务端请求伪造（SSRF）通常发生在应用接受用户提供的目标地址，再由服务器发起请求，而目标范围没有得到有效约束。风险来自请求的执行位置：服务器可能能访问用户浏览器无法直接访问的内部服务。


## 原实验中的关键代码

原后端将输入直接设置为 cURL 目标，并执行请求；以下摘录保留其关键调用，省略其他页面代码：

```php
$url = $_GET["url"];
$ch = curl_init();
curl_setopt($ch, CURLOPT_URL, $url);
curl_exec($ch);
curl_close($ch);
```

这段代码用于说明风险，不包含目标地址验证，不能直接作为安全实现。
## 历史实验

原实验提供一个“门户”功能，把表单中的 URL 传给 PHP cURL，然后将响应输出给用户。正常情况下它获取远程网页；实验又尝试使用 `file` 协议读取服务器上的文件，说明允许任意协议和目标可能造成的额外风险。

能否读取本地文件取决于 cURL 构建、允许的协议、运行账户权限以及应用设置，并不是“知道路径就能读取任意文件”。原文有一个外部网站未加载成功的观察，但没有确定原因，不能据此判断对方具备何种防护。

## 如何约束请求

如果业务只需访问固定服务，优先使用服务端维护的目标白名单。限制允许的协议、端口和目标地址；解析域名后也要检查实际连接地址和重定向目标，防止请求绕过规则。配合网络出口限制和最小权限，避免敏感内部服务仅依赖网络位置保护。

原文代码是有意脆弱的实验示例，未在本稿中重新运行；如需复现，应使用隔离且明确授权的环境。

## 原实验代码补充

以下代码用于说明历史实验的请求路径和处理逻辑，保留原有漏洞与旧版本写法。数据库密码已在原存档中隐藏；涉及外网地址的示例已替换为示例域名，具体环境需自行配置。

```html
<!-- index1.html by ailx10 -->
<html>
<head>
<title>ailx10</title>
</head>
<body>
<b>Portal!</b>

<form action="portal.php" method="get">
anything you want:<input type="text" name="url"><br />
<input type="submit" name="submit" value="submit" />
</form>
</body>
</html>
```

```php
// portal.php by ailx10
<?php
print "<b>i am ailx10,welcome to portal.</b><br />";
function portal($url)
{
    $ch = curl_init();
    curl_setopt($ch,CURLOPT_URL,$url);
    curl_setopt($ch,CURLOPT_HEADER,0);
    curl_exec($ch);
    curl_close($ch);
}
$url = $_GET["url"];
portal($url);

?>
```

这次接口的影响来自服务器所在的位置与权限。限制要放在服务端真正准备访问目标的地方，不能只因为前端输入框写着“网址”，就默认里面只会出现公网网页。
