Heartbleed（CVE-2014-0160）是 2014 年公开的 OpenSSL 内存越界读取漏洞。存在缺陷的实现没有充分验证心跳请求中声明的载荷长度，可能将请求数据之后的进程内存一起返回给对端。这是**读取越界**，不应与缓冲区写入溢出混为一谈。

本文结合历史实验理解漏洞成因；实验所用旧版系统与软件仅适合隔离环境，不应部署在生产网络。

## 心跳请求如何工作

TLS Heartbeat 扩展允许一端发送请求，让另一端返回相同的载荷。请求报文包含类型、载荷长度、载荷数据和填充数据。接收端必须根据实际收到的报文长度验证这些字段，不能只信任请求里的长度值。

以 `ABC` 为载荷的示意如下：

```text
正常请求：实际载荷 = ABC，声明载荷长度 = 3
正常响应：返回 ABC

异常请求：实际载荷 = ABC，声明载荷长度 = 1003
错误处理：按声明长度复制，可能把载荷之后的内存一并返回
```

这个例子用于说明长度不一致如何导致越界读取，实际结果还取决于报文、填充、内存布局和实现细节。响应中的额外数据不一定包含有价值的信息；重复请求也不保证取得特定内容。

## 历史实验观察

原实验在隔离的 SEED Linux 环境中使用一套存在漏洞的 OpenSSL 和 Elgg 测试站点。操作者先在站点产生会话和消息，再从另一台实验主机发送心跳测试请求，观察响应中是否出现超出预期载荷的数据。

原实验截图显示，响应中曾出现与 HTTP 请求有关的内容。截图只能说明该次实验的观察结果，不能证明所有运行环境都会泄露相同内容。原文还记录了某次把长度参数设为 22 时未观察到额外数据；这不是判断漏洞是否存在的通用阈值。

## 为什么会泄露数据

漏洞的关键在于复制长度来自请求中的声明值，而实现没有先确认接收缓冲区中确实存在相应长度的数据。下面是便于理解的**示意代码**，不是完整的 OpenSSL 源码：

```c
/* 不安全的示意：claimed_len 尚未与实际可用长度核对 */
memcpy(response_payload, request_payload, claimed_len);
```

如果声明长度超出了实际载荷，复制操作可能越过预期边界，把相邻内存写入响应。正确的处理方式是先验证整个报文中声明的长度和必要的填充是否都落在实际接收范围内；验证失败时拒绝处理。

原文引用的源码片段把释放缓冲区写在发送之前，顺序存在疑点，因此这里不将其作为可运行源码。可通过文末 MITRE 案例查看原代码及补丁的上下文。

## 防护与处置

- 使用厂商支持且已修复的 OpenSSL 和相关软件包，并确认实际运行的服务已加载修复后的库；仅更新磁盘上的文件不一定会更新正在运行的进程。
- 检查发行版的安全公告和补丁状态。发行版可能回移安全修复，因此不能只凭上游版本字符串判断是否受影响。
- 如果历史系统可能曾暴露于漏洞，评估密钥和凭据泄露风险，并根据实际情况更新证书、私钥、会话令牌及其他凭据。
- 将漏洞复现限制在获得授权的隔离实验环境。原实验中的旧系统、地址和账号均属于示例，不应视为当前部署建议。

心跳请求本该只是原样回声，却因为少了检查，把别处的内存也带了回来。回到这个最小例子，再看历史实验截图，就能区分正常载荷、额外数据和我们对结果的解释。
