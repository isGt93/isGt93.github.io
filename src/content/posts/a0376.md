ailx10说：这篇是2024年8月之前写的，后来又改过。这次我想把四层和七层的观察放到一起，于是先用 hping3 发包抓一下，再用 ab 产生 HTTP 请求，看雷池上能不能留下对应记录。前一种没在应用层界面出现，后一种能看到拦截，两边正好说明设备看的不是同一段通信。笔记还记了半开队列、重试和 SYN Cookie 的配置，方便把流量现象接回协议。做下来最该分清的，是发了什么包、哪个环节能看到它、服务有没有真的受影响，三者不应该因为工具都叫压力测试就混在一起。

---

hping3发SYN-ACK并抓包确认发出，L7雷池无记录；ab并发请求后WAF显示拦截，最后列半开队列、重试、SYN Cookie配置。

核查提示：SYN-ACK不是普通SYN半开洪泛，发包不等于有效拒绝服务，伪源不保证匿名；ab失败计数与HTTP拦截不同，u1000名义每秒1000非100。 原实验和代码未重新运行，图内细节有待核验。

接触DoS拒绝服务已经是2年前了，当时金博想带我写一篇论文，让我先研究一下DoS相关的工具，看了几篇文献，也只是浅浅的实践了一下，但终究工具都太老了，不与时俱进了。今天，碰巧一些问题，再次对上DDoS攻击。记录一下hping3 拒绝服务，这是当下比较流行的DDoS工具，可以随机化源IP地址，匿名打击。记录一下ab 压力测试工具，模拟7层DoS拒绝服务，真实源IP地址。最后，验证雷池WAF对DoS拒绝服务的防御效果。

1、模拟SYN-ACK洪泛

- 这里使用的是-i u1000 表示间隔1000微秒（帮助文档说：1秒100个报文，大雾）
- 使用参数 --flood 直接洪泛

```
hping3 -SA -p 80 -i u1000  144.34.162.13
```

![](/notes-assets/89e94f2f9f87738d678a.webp)

2、抓包确认已发送数据包（不能单凭发包证明拒绝服务）

- 这里只是想确认一下，本地确实发包出去了
- 可以看到，上面的命令使用的是真实IP地址

```
tcpdump -i eth0 -n -vvv -s 0 'net 144.34.162.13/32'
```

![](/notes-assets/3e329fb572db2391a681.webp)

- 可以使用 --rand-source 参数，让源IP地址变成虚假的IP地址，并且每个源IP地址都不一样

```
hping3 -SA -p 80 -i u10000 --rand-source  144.34.162.13
```

![](/notes-assets/cc87b4be9f17cd22065b.webp)

3、观察雷池WAF，没有一丝波澜

- 因为雷池WAF是7层防御的，所以是拦不住4层的DDoS攻击的

![](/notes-assets/839e39d14322024052e1.webp)

4、CC攻击

此步骤使用 ab 产生应用层请求；请求失败数和防护产品的拦截记录是不同指标。

```
ab -n 1000 -c 100 http://144.34.162.13/
```

![](/notes-assets/a2fe5e651b90e67339e4.webp)

6、讨论可能的缓解措施（具体配置需要结合流量类型和内核版本）

增大半开连接数

```
sysctl net.ipv4.tcp_max_syn_backlog
sysctl -w net.ipv4.tcp_max_syn_backlog=1024
```

减小重试次数

```
sysctl net.ipv4.tcp_synack_retries
sysctl -w net.ipv4.tcp_synack_retries=1
```

开启 TCP SYN Cookies

```
sysctl net.ipv4.tcp_syncookies
sysctl -w net.ipv4.tcp_syncookies=1
```

为防止重启服务器，配置丢失，可以永久保存至`/etc/sysctl.conf`

```
net.ipv4.tcp_syncookies = 1
net.ipv4.tcp_synack_retries = 1
net.ipv4.tcp_max_syn_backlog = 1024
```

发出了多少包、服务还能不能用、页面拦了哪些请求，需要分别记录。把这些指标摆在一起以后，才比较容易发现测试本身有没有选错报文，或者把不同层的结果混在了一起。
