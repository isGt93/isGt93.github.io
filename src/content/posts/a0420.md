ailx10说：这篇是2022年1月之前写的，后来又改过。HTTP 代理这回我用 reGeorg，把 PHP 隧道放到跳板网站，再接本地 SOCKS 和 proxychains。扫描里能发现端口，接着试远程桌面、网页和 SMB，却没有按预想顺利。这个落差让我把笔记写成了一半通、一半没通的真实状态。知道端口在那里，和上层协议真的能完成交互是两回事，隧道脚本、环境权限与协议细节都可能挡在中间。我把这些尝试留下，是想以后继续排查时有个起点，而不是因为一次失败就断言工具只会扫描。

---

今天是周一，领导又强调了一遍，全员写专利。我分到3个专利指标，仅次于领导的专利数。今天开始写第2个发明专利了，大体是通过皮尔逊相关系数和条件概率计算安全事件的可信度。在网络安全领域里3年的工作经验，加上信息安全科班出身，企业安全的整个发展过程看的一清二楚，作为网络安全研究员，开始布局高端安全领域。

本文记录历史 reGeorg 测试：端口探测有结果，RDP、Web 和 SMB 等后续尝试失败。单次失败不能证明工具只能扫描，还需核对服务端实现、代理配置和协议兼容性。

```
https://github.com/sensepost/reGeorg
```

## 第一步：在ubuntu18跳板机上投递隧道文件

- 先在ubuntu18跳板机上clone项目
- 然后把隧道文件复制到网站根目录中

![](/notes-assets/6d3bdf39f6e73f524537.jpg)

## 第二步：在kali rolling配置proxychains.conf

- 修改最后一行
- 端口要和后面保持一致

![](/notes-assets/25df25631be6737268f4.webp)

## 第三步：在kali rolling上启动代理

- 端口10101与第二步保持一致
- 192.168.160.137是跳板机

```
python reGeorgSocksProxy.py -u http://192.168.160.137/tunnel.nosocket.php -p 10101
```

![](/notes-assets/29ea3f5faaf505cd50b0.jpg)

## 第四步：在目标机器开启防火墙，阻断kali rolling的访问

- 保证kali rolling无法访问目标机器

![](/notes-assets/bdd7e3391fc7969ce318.webp)

## 第五步：在kali rolling上探测目标机器开放的端口

- 使用代理进行端口扫描
- 成功（ tunnel.nosocket.php）

```
proxychains nmap -sT 192.168.160.1
```

![](/notes-assets/f4e325f666bfaaf47e76.jpg)

- 使用代理进行rdesktop远程连接
- 只告诉3389端口开放，并没有成功，差评（ tunnel.nosocket.php）

![](/notes-assets/e4eb9e69c54e90c80100.jpg)

- 使用代理访问目标主机的网站
- 也没有成功，差评（ tunnel.nosocket.php）

![](/notes-assets/5ca30af6985ef230f425.jpg)

- 445端口暴力破解
- 发现神秘的阻力，导致不管用不用代理，都无法暴力破解目标主机

```
hydra 192.168.160.1 smb -L user.txt -P pass.txt -V
```

![](/notes-assets/be7844a7f0f91a01b1e1.jpg)

- 但是换了一台主机，暴力破解成功了
- 说明hydra smb暴力破解的用法没问题

![](/notes-assets/93dcbc36e83bfbf6af60.jpg)

- 配置代理之后，发现并不能暴力破解
- 差评（ tunnel.nosocket.php）

![](/notes-assets/b7ba48eaf7e9a1b286f5.jpg)

本篇完～

这些失败不能简单归成“工具只会扫描”。先留住隧道脚本、权限、目标直连状态和协议表现，后面才有条件找出是哪一段支持得不够。
