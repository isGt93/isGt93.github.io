ailx10说：这篇是2022年12月之前写的，后来又改过。看过一些传统 WAF 之后，我开始琢磨 API 越来越多时，原来的防护框架怎么扩展到 WAAP。于是从 Log4j 的变形、风险评分、云情报和机器学习往下读，又把 API 资产发现、测试和行为基线记在一起。写这篇更像整理一个研究方向，而不是亲手验证了某个产品所有宣传。让我感兴趣的是，接口从“能识别”到“知道谁在做什么”之间还有很长一段，令牌、权限和业务流程也不会因为多了一层设备就自动变清楚。

---

Web 应用防火墙（WAF）可以检查和过滤 HTTP 请求，帮助识别部分常见攻击；Web 应用及 API 防护（WAAP）通常在此基础上，结合 API 安全、流量管理和其他防护能力。不同产品的实现差异较大，名称本身不能保证某项能力。

## 为什么 API 需要单独关注

Web 系统除了页面，还通过 API 处理订单、账户和数据。部分风险与单一请求的语法无关，例如用户能否访问别人的订单、价格是否由服务端重新计算、验证码是否被滥用。即使请求经过 WAF，这些业务规则仍需应用在服务端验证。

API 防护通常需要结合资产梳理、身份认证、对象级授权、输入校验、速率限制和日志监测。持有有效令牌只说明请求具备某种身份，不能代替每次对象访问的授权检查。

## 以 Log4j 为例理解检测边界

历史 Log4j JNDI 问题说明攻击输入可能经过不同编码或变形。只匹配单一字符串的规则容易遗漏变体；语义分析、规则更新和威胁情报可以提供补充，但不能保证识别所有变体。LDAP 查询与可能发生的 HTTP 资源获取属于不同阶段，具体行为取决于版本、配置和运行环境。

对受影响系统，防护重点仍是识别资产、使用厂商修复版本并核查相关配置。网络过滤是纵深防御的一层，不能替代修补和权限控制。

## 如何评估防护能力

- 确认产品能否覆盖实际使用的域名、API、协议及部署架构。
- 用授权的测试样本分别评估检测率、误报和对业务的影响。
- 审查 API 清单、认证和对象级授权，并在应用内修复根因。
- 将防护日志与服务端日志关联，建立可持续的规则调整和响应流程。

原文列举了厂商产品能力和历史行业统计；缺少独立验证的数据不作为本文的结论。实际能力应以部署版本、配置和测试结果为准。

看产品介绍时，功能名很容易把人带着走。我更想带走的是可验证的问题：接口有没有发现，权限有没有查，异常依据是什么。把这些问清，比把宣传里的承诺原样搬进方案更有用。
