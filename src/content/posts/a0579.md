ailx10说：这篇是在2024年3月之前写的，后来又改过。PyInstaller 不再直接提供那套加密参数后，我又试了先用 Pyarmor 处理代码，再交给 PyInstaller 打包。入口和 src 都做一遍，最后重新解包，看看拿回来的究竟是原逻辑，还是一层运行包装。这篇把那次工具组合的过程留下，也看了期限和硬件绑定这些选项。它延续的是前面源码保护的那条线：每换一种办法，都别只看宣传或打包成功，得反过来拆一次，才能知道这回真正改变了什么。

---

用Pyarmor8.5.1混淆入口和src，再PyInstaller打包，解包只恢复加密包装代码，并介绍期限及硬件绑定。

核查提示：一个解包器未恢复不证明安全，2024未见工具声明非当前事实；运行时依赖和版本兼容须明确。 旧环境及截图细节未逐项核验。

本文记录 PyArmor 8.5.1 混淆后用 PyInstaller 打包的历史实验。一个提取工具未恢复源码不能证明无法逆向，还需检查运行时与版本兼容。

Pyarmor 是一个用于加密和保护 Python 脚本的工具，它能够保护 Python 脚本代码不被泄露，此外还支持设置加密后脚本的使用期限，绑定加密脚本到硬盘、网卡等硬件设备，有点类似license控制，确实有点东西。实验过程如下：

1）加密前，python代码都是明文

```
# 加密前的 a.py
from src.b import bb
if __name__ == '__main__':
    bb(1, 1)
```

2）经过pyarmor v8加密[\[1\]](#ref_1)

```
pyarmor gen a.py
```

4）同理，对src包进行加密

```
pyarmor gen -O dist2 -r -i src
```

6）使用pyinstaller 将自己的包和主函数，一起打包

```
pyinstaller -F --add-data "src;src" a.py
```

![](/notes-assets/e62647b3876978287028.webp)

7）将加密的src包，以及主程序的加密辅助包，一起复制到打包后的dist目录中，成功运行exe

![](/notes-assets/4a5f0843915fc145cfee.webp)

8）使用 pyinstxtractor-ng 解包

```
pyinstxtractor-ng.exe a.exe
```

![](/notes-assets/3b4ca99653067846ef40.webp)

9）使用uncompyle6 解密主程序 `a.pyc`，发现是 pyarmor 加密后的`a.py`文件，win了～

```
uncompyle6 a.pyc
```
