ailx10说：这篇是我2024年12月写的。Cat 这题里，一个非法字节把 Django 的调试页面带了出来，后端源码和 SQLite 路径一下多了很多线索。顺着这些信息，我继续尝试请求，最后拿到了数据库相关内容。不过中间 PHP 怎样转发、那个带 @ 的路径为什么会把文件读出，当时我并没有解释完整。这篇把成功的观察和没想明白的地方都放着，没有把“拿到结果”写成“机制已经讲透”。它很适合回头追问：报错究竟泄露了什么，后面每一步又靠了哪条信息？

---

原记录通过异常响应观察到 Django 调试信息，并看到数据库路径。后续带 @ 的输入出现数据库内容，但前后端转发实现缺失，原因不能直接归结为 ping 读取文件。

![](/notes-assets/7d031295fa31c8aacd41.webp)

输入域名，仅URL发生了变化，除此之外没有任何反应，输入 `127.0.0.1` 发现是一个 Ping 命令

![](/notes-assets/ab63282698ac81b762a5.webp)

尝试命令执行，但是输入有校验，不能输入`|&;%*` 等 ，但是可以输入 `@`

![](/notes-assets/be56872f71dcea3d7a18.webp)

输入 %99 后原题返回异常页面；它是一个非 ASCII 字节，不能笼统称为“宽字符”。截图显示当时使用 Django 1.10.4 和 Python 2.7.12。

```
GET /index.php?url=%99 HTTP/1.1
```

![](/notes-assets/63db578b87cac16dc4a2.webp)

对\<code\>之间的内容进行解码，得到报错代码明文

```
import html

from bs4 import BeautifulSoup



encoded_str = r"""<code>.......</code>"""

decoded_str = html.unescape(encoded_str)

decoded_str = BeautifulSoup(decoded_str, "html.parser").text



# 打印解码后的字符串

print(decoded_str)
```

可以看见代码片段，审计代码，这里是POST请求，很奇怪，前端是GET请求，应该是后端改成了POST请求

![](/notes-assets/7a00413f6974754c1115.webp)

原作者记录输入 @ 和数据库绝对路径后出现内容，但同时明确表示原因不清楚。旧 PHP/cURL 的 @ 文件上传语义可能相关，缺少桥接代码不能确认。

这题拿到了信息，却没有把转发和读文件的原因完整走通，缺口就留在这里。结果能帮助定位问题，机制还要另找证据，二者不必被强行写成同一份完整解释。
