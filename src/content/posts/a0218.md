ailx10说：这篇是我2023年9月写的。这道 Django 实验，第一次提交用户名还不够，第二次才是关键。我把带脚本内容的名字再次拿去创建用户，让重复用户触发异常，然后看调试错误页怎样把输入展示出来。它和普通页面里存下脚本、再等别人浏览的感觉不太一样，入口实际藏在错误处理里。笔记因此主要记了两次操作的差别：为什么前一次只是准备，后一次才走到有问题的页面，也提醒我别只盯正常业务页，调试信息同样会处理不可信输入。

---

原文以 Django 调试页面的历史 XSS 为例；应核对 CVE 对应的受影响版本与发行版补丁。

前提：准备好docker环境，下载好vulhub，进入目录 ，开始复现漏洞

- `docker-compose build //可选`
- `docker-compose up -d`

完成试验后，记得删除漏洞环境哦～～

实验结束后可在确认项目目录和 Compose 配置后关闭该项目的服务；原文的全局 Docker 清理命令已移除。

页面响应只能说明服务可访问，仍需确认调试模式、异常条件和版本。

![](/notes-assets/31928b90d5bd4c8fa39d.webp)

先创建用户：\<script\>alert(520)\</script\>

```
http://144.34.162.13:8000/create_user/?username=<script>alert(520)</script>
```

原实验第二次提交相同用户名以触发异常，并在错误页观察到脚本执行；实际触发依赖数据约束和错误页面。

调试页本来是帮开发者看问题的，也可能把不可信内容带进页面。把异常触发和输出位置分别记下来，才能解释为什么普通注册没有显现的问题，会在报错时冒出来。
